# /great-resume：简历提升

把用户做过的事情翻译成招聘方容易理解、可以继续追问、也能由证据支撑的表达。简历提升是岗位定位和证据组织，不是虚构头衔、公司、项目、技术栈或数据。

## 工作流程

1. 先确认目标岗位、岗位描述、求职渠道和用户希望突出的方向。
2. 读取现有简历、项目说明、作品集、公开仓库或用户提供的截图；跨 Skill、存在冲突或包含强主张时，按 [主张—证据账本](references/claim-evidence-ledger.md) 创建或更新事实基线；涉及商业分析、策略运营、经营复盘或 AI 产品化经历时，额外按 [商业分析证据工作流](references/business-analysis-evidence.md) 区分结果性质、个人动作和可追问证据。材料不足时先基于已有事实给初稿，并列出最多 5 个关键待补项。
3. 输出 1—3 个岗位定位，区分稳妥版和进取版；进取版必须说明需要补充的证据。
4. 按“动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界”重写经历和项目要点。
5. 生成简历摘要、Boss 直聘/微信 HR 短开场白，以及一版稍完整的自我介绍。
6. 用“原始说法—建议写法—事实证据—个人边界—风险/待确认”审计每个强主张；使用账本时同步更新候选表述、确认状态和可展开的面试细节。

## 表达边界

- 正式职位、公司、时间和教育背景保持真实。
- 只有能说明决策、交付和结果时，才使用“主导”“负责人”“Owner”等强动词。
- 没有可靠数字时使用可核验的定性结果，不编造百分比、用户量、延迟或排名。
- 对没有直接负责的内容明确写“团队负责”或“待确认”，不替用户冒领。
- 用户要求制作 HTML/PDF 文件、复刻 ASu 同款或选择简历模板时，转入 `/make-resume` 模式。

## 智能应用开发方向取向

面向"智能应用开发工程师（Java + Python / AI 应用）"类岗位组织表达时，按以下取向改写：

- **双栈定位**：Java（Spring Boot / Spring Cloud / MySQL / Redis）写工程底盘与业务系统能力，Python（FastAPI / LangChain / LangGraph）写 AI 应用能力；既不写成纯 CRUD 后端，也不写成只会调 API 的算法包装。
- **AI 项目链路化改写**：按"场景问题 → 数据/知识处理 → 检索或编排 → 生成/交互 → 工程化 → 结果证据"拆解 RAG / Agent / LLM 应用经历；每个环节写清选型与动作（如向量库双层索引、混合检索融合、精排截断、流式输出与会话落库），技术名词后必须跟动作或理由。
- **Java 项目改写**：按"业务场景 → 核心接口与数据设计 → 性能/稳定性动作 → 量化结果"组织，突出缓存、批量处理、权限、并发等工程动作。
- **量化口径**：区分项目总量与个人贡献（例如项目代码行数、服务用户数是项目口径），没有实测数据时用可核验的定性结果，不编造准确率、QPS 或用户量。

## 默认输出

除非用户只要其中一项，否则按以下顺序交付：

1. 一句话岗位定位；
2. 简历顶部摘要；
3. 2—4 条项目/经历改写；
4. HR 开场白短版和完整但简洁版；
5. 证据补强清单与可能追问。

组合使用 `/make-resume` 时，同时交付更新后的主张—证据账本；只生成简单短文案时不强制创建。

Boss 直聘或微信开场白默认控制在约 80—160 字，先说身份和方向，再说一个真实成果，最后邀请继续交流。
